  为什么扩张不用 Triton

  从当前代码看，扩张实际使用 F.pad，不是 Triton：

  vllm_speculative/vllm/worker/cache_engine.py:296

  self.gpu_cache[i] = F.pad(self.gpu_cache[i], (..., 0, increase_num_blocks))

  原因可以从实现推断出来：

  1. 扩张本质需要创建更大的 tensor storage。Triton kernel 只能在已有 tensor 指针上做 load/store，不能替
     PyTorch 重新分配 gpu_cache[i] 的 storage 或改变 tensor shape。
  2. 新增块是空 KV 空间，不需要复杂迁移；旧块顺序不变，直接用 F.pad 让 PyTorch 完成新 tensor 分配、旧内容复
     制、新区域填充即可。
  3. 之前尝试过 torch.cat + zeros，代码注释写了 ThreadPoolExecutor 版本 “会 OOM”。所以现在选择 F.pad 作为较简
     单的扩张实现。
  4. Triton 更适合收缩时的“把尾部仍被占用的 block 搬到前面空闲 block”这种按 block id 的稀疏迁移；这也是
     block_migration_map 存在的原因。扩张没有这种映射搬迁需求。

  一句话：扩张是重新分配更大 KV tensor，Triton 管不了分配和 shape；收缩需要按 block 映射搬数据，Triton 正好适
  合做这个数据平面拷贝。
